# Linux RTX 4060 measurement record — 2026-11-23

## Status and scope

Physical-GPU correctness passed with the existing debug CLI; the release timing campaign remains pending a verified release executable on the target machine. The debug suite completed with exit 0 and is documented separately below. No release performance distribution or CPU speedup is claimed.

The CPU-only harness checks passed: four tests covered chunked fixture verification and corruption detection, nearest-rank percentile calculation, JSON report extraction, and a bounded timeout with an observed child exit. The command was `python3 -B scripts/measure.py --self-test`, exit 0. These checks do not establish GPU correctness or performance.

This experiment asks how much time a fresh zaccel command spends in setup, transfers and completion, and how its individual dispatch observations behave when one process reuses its device, pipeline and buffers. It does not compare zaccel against an optimized CPU implementation.

## Reproduce after executable release

Run from the repository root after the coordinator identifies the ready executable. The output directory must be new; the script refuses to overwrite an earlier attempt.

```sh
python3 -B scripts/measure.py \
  --bin /var/tmp/project-z-cargo-target/release/zaccel \
  --adapter-name 'RTX 4060' \
  --samples 10 --iterations 20 --warmup 3 \
  --timeout-ms 30000 --process-timeout 45 \
  --sample-interval-ms 100 \
  --output-dir artifacts/measurements/astra-84625865-linux-rtx4060-20261123-v1
```

The script does not build, install, publish or invoke CI. It records the executable's actual version and SHA-256 before the suite and checks the hash again afterward. Source, lockfile and measurement-script hashes identify the observed checkout; a dirty checkout is recorded rather than presented as a clean release commit.

All input and result buffers live in an OS temporary directory. Only JSON reports, command output and textual shaders/manifests are retained in the ignored measurement directory. The complete command receipt is saved before a failure is raised. A timeout stops the suite; it does not trigger an automatic GPU retry.

## Workload and measurement units

The required workload is 1,048,576 independent f32 additions using the shipped vector-add shader and 64 invocations per workgroup. It dispatches 16,384 workgroups. Its input has two little-endian floats per element, and its output has one. Input construction and result verification process at most 16,384 elements per chunk, outside the timed CLI invocation.

The fixture values are bounded binary fractions. The reference computes the intended addition and rejects non-finite, truncated or incorrect output. Reference execution time is recorded only as verification overhead; it is not a CPU benchmark or a basis for a speedup claim.

Accounted buffer sizes for the required workload, derived from the plan:

| Allocation | Bytes | MiB |
| --- | ---: | ---: |
| Resident input and output | 12,582,912 | 12 |
| Upload staging | 8,388,608 | 8 |
| Output readback staging | 4,194,304 | 4 |
| Total before optional timestamp buffers | 25,165,824 | 24 |
| Optional timestamp resolve and readback | 32 | 0.000031 |

The default accounted GPU budget stays at 268,435,456 bytes. This accounting does not measure driver allocations or exclusive device VRAM. The optional 4,194,304-element case additionally requires at least 2 GiB of observed host MemAvailable and a dispatch shape supported by the selected adapter. It is not part of the required initial command.

For each admitted count, the script alternates ten fresh `run` processes with ten fresh `bench` processes. A run process submits one dispatch without warmup. A bench process performs three warmups and twenty measured dispatches with the same resources and retained buffer state. “Fresh process” describes process lifetime; neither the driver shader cache nor the OS file cache is cleared.

Statistics retain min, median, nearest-rank P95 and max. For N values, P95 is sorted value ceil(0.95 × N). Whole-process observations are summarized across the ten process invocations. Dispatch observations are also pooled for descriptive statistics, but are not presented as 200 independent process replicates. Per-process dispatch medians are retained separately.

## Timing boundaries

Each quantity keeps its original scope. Subtracting two of these clocks is not used to infer an unmeasured hardware stage.

| Quantity | Recorded interval |
| --- | --- |
| Whole CLI wall time | External process creation through output collection and observed exit; includes supervision and sampling overhead. |
| Preparation | Worker-side shader and input planning before native execution. |
| Initialization | Execution-layer validation, adapter selection and device setup. |
| Pipeline | Compute pipeline creation and bind-group setup. |
| Upload | Resident/staging allocation and the initial upload submission/completion stage. |
| Host dispatch | Queue submission through completion wait; includes timestamp copies when enabled, excludes command encoding and later timestamp mapping. |
| Hardware kernel timestamp | Optional compute-pass timestamp difference, converted using the device period; unavailable values remain null. |
| Readback | Final output copy, map and host extraction. |
| Execution total | The execution layer, including warmups and other work not isolated in a listed stage. |
| Output write and worker total | Result writing, and the broader worker-side path respectively. |

The implementation and public timing fields are in [gpu.rs](../../src/gpu.rs), [main.rs](../../src/main.rs) and [validation.md](../validation.md). The measurement logic is in [measure.py](../../scripts/measure.py).

## Required correctness evidence

The existing acceptance suite runs first with `--require-gpu`, 4,096 elements, twenty measured iterations and three warmups. It must validate the shipped addition, multiplication and affine shaders, then verify their GPU results, the uniform manifest, raw stdin/stdout, inline WGSL and benchmark output. Missing hardware is a failure in this mode.

The measurement harness then executes small bounded boundary cases:

| Case | Observable requirement |
| --- | --- |
| Short in-place input | Two u32 inputs initialize a four-u32 buffer. Adding ten yields 11, 12, 10, 10, including the zero-filled tail. |
| Retained state | Two warmups plus three measured increments yield five in every element. |
| Exact allocation budget | A 16-byte output plus 16-byte readback succeeds with a 32-byte budget; optional timestamp buffers are omitted and kernel timing is null. |
| Group gap and multiple outputs | Group 0 and group 2 bindings both produce independently checked results. |
| Software index without opt-in | If a software adapter is present, explicitly selecting it without software permission fails for that reason. If absent, this case is unsupported. |

No unbounded shader, forced out-of-memory workload or driver-hang experiment is included. Each child process has a bounded timeout and an explicit exit receipt. A process timeout cannot establish that a previously submitted GPU operation has stopped.

## Evidence and interpretation limits

The debug functional run recorded the current adapter, backend, driver, CPU, kernel, installed compiler, binary identity, host MemAvailable and system load. The release campaign will capture its own observations again. The earlier inventory is not substituted for these snapshots; unknown source-commit metadata remains explicitly unknown.

Optional /proc sampling observes the CLI parent and discovered child processes every 100 ms. Its largest observed RSS sum can miss short peaks and double-count shared pages; it is neither exact peak memory nor PSS/USS. NVIDIA memory snapshots describe the whole device, which can include the desktop, caches and other clients. They cannot be interpreted as exclusive zaccel allocation. Shared-host load, clocks and thermal conditions are not controlled.

### Review questions

- **Contribution:** The record separates command startup, resource setup, transfers and dispatch intervals; it does not propose a new GPU algorithm.
- **Clarity:** Commands, sample counts, units, percentile rule and timing boundaries are explicit.
- **Experimental strength:** The listed debug GPU behaviors passed. Release performance conclusions remain pending the timing campaign; CPU reference speed is not used as a baseline.
- **Completeness:** Correctness, requested boundary behavior and one physical Linux GPU are in scope. Other hardware, operating systems and workloads remain unmeasured.
- **Design soundness:** Default buffer budgets, bounded subprocesses, chunked verification and stop-on-failure behavior constrain this experiment. They do not provide driver-reset guarantees.
